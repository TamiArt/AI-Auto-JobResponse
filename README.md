# HuntPulse AI

Прототип бесплатного ассистента для поиска вакансий и подготовки персонализированных откликов — аналог сценариев Sofi Assistant. Текущая версия является **клиентским UX-прототипом**: поиск, история, счётчики, проверка HH-профиля и отправка отклика пока симулируются. Интерфейс не должен восприниматься как готовый бот, который уже отправляет отклики работодателям.

## Быстрый старт

Требования: Node.js 20+ и npm 10+.

```bash
npm install
npm run dev
```

Проверка production-сборки:

```bash
npm run check
```

## Что уже хорошо

- Цельный адаптивный интерфейс: onboarding, дашборд, ручная очередь, поиск, история, настройки и руководство.
- Светлая/тёмная темы, понятные состояния загрузки и статусы операций.
- Выбор нескольких бесплатных AI-провайдеров и источников вакансий.
- Проверка импортируемого JSON и явные ссылки на внешние источники.
- Ручной режим подтверждения снижает риск нежелательных массовых откликов.
- Поиск не ограничен IT: предусмотрены разработка, тестирование, дизайн, иллюстрация, искусство, управление, маркетинг, данные, поддержка и произвольная профессия.
- Каталог охватывает 28 универсальных, IT, творческих, государственных, удалённых и фриланс-площадок; для каждой формируется собственная безопасная ссылка поиска.

### Подключение интернет-площадок

Фраза «все площадки интернета» не может быть конечным проверяемым списком: сервисы появляются, закрываются, меняют URL, географию, правила и доступность API. Поэтому приложение использует расширяемый реестр `data/jobSources.ts` и два безопасных режима:

1. `public-api`/`rss` — кандидат на серверную агрегацию только после проверки актуальной официальной документации и условий использования.
2. `external-search` — бесплатный переход в поиск площадки с уже заполненной профессией; авторизация, CAPTCHA и ограничения не обходятся.

Сейчас представлены российские и международные агрегаторы, IT-площадки, удалённая работа, государственные порталы, Behance, Dribbble, ArtStation и фриланс-биржи. Наличие площадки в каталоге не означает, что прототип тайно загружает или отправляет туда данные пользователя. Реестр можно расширять одной декларативной записью без изменения UI поиска.

## Модульная структура frontend

- `domain/` — предметные типы без зависимости от React.
- `data/` — реестры источников, профессий и демонстрационные данные.
- `lib/` — чистая валидация и инфраструктурные функции.
- `features/` — изолированные пользовательские сценарии поиска, позиций, настроек и руководства.
- `shared/` — переиспользуемые UI-компоненты.
- `App.tsx` — только состояние верхнего уровня и композиция features.

Новый код не должен возвращать предметную логику в `App.tsx`. Целевой предел — до 700 строк на файл; превышение требует декомпозиции, а не исключения из правила.

## Результаты технического и системного аудита

### Критические недостатки

1. **Нет реальной интеграции.** `generateResults`, данные откликов, очередь, счётчики и задержки — mock. Нельзя показывать их как актуальные данные.
2. **Состояние верхнего уровня пока централизовано.** UI и предметные данные уже разнесены по модулям, но следующий шаг — вынести storage и orchestration из `App.tsx` за тестируемые adapters/hooks.
3. **Секреты в браузере.** В полностью клиентском приложении ключ доступен исполняемому JavaScript. После исправления он хранится только в `sessionStorage` и исключён из экспорта, но production-решение должно использовать локальный backend/BFF и шифрованное хранилище.
4. **Нет backend, БД, очереди и планировщика.** Автопоиск не продолжит работу после закрытия вкладки, нет retry, rate limiting, идемпотентности и аудита.
5. **Нет автоматических тестов, линтера, typecheck в CI, телеметрии ошибок и accessibility-аудита.**

### Повторы и неиспользуемый код

- Повторяются Tailwind-строки полей, карточек, кнопок и бейджей; часть уже скрыта в `Field`, `StatusBadge`, `SourceTag`, но нужны общие примитивы.
- Реестр источников содержит `rss`/`api`, однако приложение их не вызывает.
- `relativeTime` не преобразует дату и только возвращает аргумент.
- Несколько UI-компонентов в `src/app/components/ui/` и изображение `src/imports/image.png` не импортируются приложением. Перед удалением следует подтвердить, что они не являются заготовкой дизайн-системы; затем оставить только реально используемые компоненты.
- `ConfigPanel` дублировал сохранение импортированного конфига; исправлено — сохранением управляет единый callback.

### Исправлено в текущей итерации

- Добавлена строгая проверка диапазона `dailyLimit`, включая `NaN` и бесконечность.
- API-ключ исключён из JSON-экспорта и постоянного `localStorage`; токены позиции и ключ живут только в рамках вкладки.
- Добавлена очистка таймера при размонтировании приложения.
- Демо-поиск и демо-история явно помечены, ложное заявление о готовой PWA удалено.
- Добавлен `.gitignore`, нормализованы имя пакета и единая команда проверки.
- Монолитный `App.tsx` разделён на `domain`, `data`, `lib`, `features` и `shared`; каждый исходный файл укладывается в предел 700–800 строк.
- Каталог профессий и демо-сценарии расширены за пределы IT: поиск принимает любую должность и предлагает направления для QA, дизайна, иллюстрации, искусства и других специализаций.

## Целевая бесплатная архитектура

Все компоненты можно запустить локально или на собственном сервере без платных API:

- **Frontend:** React + Vite + TypeScript (текущий стек).
- **Backend/BFF:** FastAPI или NestJS.
- **База:** PostgreSQL; для одиночной локальной установки допустим SQLite.
- **Очереди и расписание:** Redis + BullMQ либо PostgreSQL + `pg-boss`; для MVP — cron/APScheduler в одном процессе.
- **AI:** локальный Ollama с Qwen/Llama/Mistral; опционально бесплатные квоты Gemini/Groq/OpenRouter, без обязательной зависимости от них.
- **Парсинг:** только официальные публичные API/RSS и разрешённые пользовательские OAuth-сценарии. Не обходить CAPTCHA и ограничения площадок.
- **Тесты:** Vitest + Testing Library, Playwright, pytest/Jest, axe-core.
- **Наблюдаемость:** OpenTelemetry + Prometheus + Grafana + Loki либо минимально структурированные JSON-логи.
- **CI:** GitHub Actions или GitLab CI на бесплатных лимитах; локальный эквивалент — pre-commit hooks.

## План улучшений

План выполняется последовательно. Нельзя начинать этап, пока не выполнены его критерии выхода. Каждый пункт оформляется отдельным небольшим PR; рефакторинг не смешивается с изменением поведения.

### Принципы, защищающие текущий функционал

1. **Сначала фиксируем поведение тестами.** До перемещения кода создаются smoke/E2E-тесты пяти текущих маршрутов: onboarding, добавление позиции, поиск, ручная очередь, импорт/экспорт настроек.
2. **Strangler pattern вместо переписывания.** Новый feature-модуль подключается за прежним интерфейсом; старый код удаляется только после parity-теста. Большого одновременного rewrite не будет.
3. **Feature flags.** Реальный backend, источник и AI включаются независимо. При ошибке пользователь возвращается в безопасный preview, а не получает сломанный экран.
4. **Контракт прежде реализации.** Frontend зависит от TypeScript-интерфейса и mock adapter, а не от конкретного HTTP API. OpenAPI-клиент генерируется и не редактируется вручную.
5. **Forward-only migrations.** Изменение БД сначала добавляет совместимые поля/таблицы, затем переводит чтение, и только в следующем релизе удаляет старое. Для каждого шага есть backup и проверенная команда восстановления.
6. **Бесплатность — обязательный acceptance criterion.** Основной локальный путь не требует карты и внешнего AI API. Бесплатные квоты облачных провайдеров считаются только опциональными и не являются гарантией.

### Этап 0 — baseline и страховочная сетка

**Цель:** получить измеримую точку отсчёта без изменения пользовательского поведения.

- [ ] Зафиксировать поддерживаемые Node.js/npm в `.nvmrc`/`engines` и сделать воспроизводимый lockfile.
- [ ] Добавить TypeScript `noEmit`, ESLint, Prettier и проверку неиспользуемых импортов; сначала warning, после очистки — обязательный CI gate.
- [ ] Подключить Vitest + Testing Library и Playwright; сохранить скриншоты desktop/mobile для светлой и тёмной тем.
- [ ] Покрыть тестами `validateImportedConfig`, безопасный экспорт, session storage и очистку таймера.
- [ ] Создать E2E smoke suite текущего UX и accessibility smoke через `@axe-core/playwright`.
- [ ] Записать начальные метрики: размер bundle, время сборки, число console errors и Lighthouse-показатели.

**Критерий выхода:** чистая установка и все проверки проходят одной командой `npm run check`; изменения UI подтверждаются visual diff. Откат — revert одного атомарного коммита.

### Этап 1 — безопасная декомпозиция frontend

**Цель:** убрать монолит, не меняя интерфейс и mock-поведение.

- [ ] Вынести `domain`-типы и чистые функции в `src/domain/` с unit-тестами.
- [ ] Вынести mock fixtures в `src/mocks/`, storage в версионируемый adapter, общие элементы — в `src/shared/`.
- [ ] По одному извлечь features: `settings` → `positions` → `search` → `applications`; после каждого шага запускать smoke и visual regression.
- [ ] Удалить только подтверждённо неиспользуемые UI-файлы и зависимости; проверять импорт через статический анализ и production build.
- [ ] Добавить Error Boundary и понятное восстановление повреждённого local/session storage.

**Критерий выхода:** `App.tsx` только компонует features; snapshots/E2E до и после совпадают, bundle не вырос более чем на 5% без обоснования.

### Этап 2 — локальный BFF и данные

**Цель:** создать реальную основу, сохранив работающий mock fallback.

- [ ] Выбрать **один** простой стек для MVP: FastAPI + SQLite. PostgreSQL подключать позднее через тот же repository interface; Redis пока не нужен.
- [ ] Описать OpenAPI-контракт и health endpoint; добавить frontend adapter `mock | http`, переключаемый feature flag.
- [ ] Реализовать сущности profile, search, vacancy, application и event; дедупликация по `(source, vacancy_id, resume_id)`.
- [ ] Хранить секреты только на локальном backend: OS keyring, а при его отсутствии — шифрованный файл с паролем пользователя. Никогда не возвращать секрет во frontend.
- [ ] Добавить schema migrations, резервную копию SQLite перед миграцией и integration tests на чистой и обновляемой БД.
- [ ] Подготовить `docker compose` как удобную, но необязательную альтернативу обычному локальному запуску.

**Критерий выхода:** приложение полностью работает offline в mock-режиме и локально через BFF; отключение BFF не теряет введённые данные и показывает управляемую ошибку.

### Этап 3 — первый реальный источник, только чтение

**Цель:** заменить фиктивный поиск реальными данными с минимальным риском.

- [ ] Проверить условия использования и выбрать один официально разрешённый публичный API/RSS; если подходящего нет, оставить переход на поисковую страницу без scraping.
- [ ] Реализовать общий `JobSourceAdapter`, нормализацию, timeout, rate limit, retry с jitter и кеш SQLite.
- [ ] Показывать `fetchedAt`, источник, состояние свежести, частичный результат и диагностируемую ошибку.
- [ ] Добавить contract tests на сохранённых обезличенных fixtures; сетевые тесты не должны быть обязательны для CI.
- [ ] Не отправлять отклики: результат открывается на площадке или добавляется в локальный список review.

**Критерий выхода:** повторный поиск не создаёт дубликаты; недоступность источника не ломает mock/кеш; никакой CAPTCHA или запретный scraping не обходится.

### Этап 4 — профиль, скоринг и бесплатная генерация

**Цель:** полезные черновики без выдуманных фактов и обязательных платных API.

- [ ] Сначала реализовать детерминированный шаблон письма и объяснимый rule-based scoring — они работают без AI.
- [ ] Добавить локальный Ollama как опциональное улучшение; маломощным устройствам оставить шаблонный режим.
- [ ] Изолировать текст вакансии как недоверенные данные, ограничить длину и защитить prompt от инструкций внутри вакансии.
- [ ] Разрешать модели использовать только факты из профиля; отображать использованные факты и предупреждать о неподтверждённых утверждениях.
- [ ] Gemini/Groq/OpenRouter оставить выключаемыми адаптерами бесплатных квот, без обещаний постоянной доступности.
- [ ] Перед любым действием пользователь просматривает и редактирует черновик.

**Критерий выхода:** при выключенных сети и Ollama создаётся валидный шаблонный черновик; golden tests подтверждают отсутствие добавленных достижений.

### Этап 5 — контролируемые действия и надёжность

**Цель:** автоматизировать только разрешённые площадкой операции.

- [ ] Для каждого источника отдельно подтвердить наличие официального API отправки и требования OAuth. Если API нет — оставить ручной переход.
- [ ] Ввести preview по умолчанию, явное подтверждение, дневной лимит, quiet hours и глобальную кнопку остановки.
- [ ] Добавить idempotency key, audit event и конечный автомат статусов; повторный запуск не повторяет side effect.
- [ ] Начать с очереди в SQLite/процессе. `pg-boss`/Redis добавлять только при доказанной необходимости нескольких workers.
- [ ] Реализовать bounded retry, dead-letter состояние и ручное безопасное повторение.
- [ ] Добавить экспорт и полное удаление данных, отзыв токенов и настраиваемый срок хранения.

**Критерий выхода:** интеграционные тесты доказывают отсутствие двойной отправки при retry/перезапуске; kill/restart не теряет состояние; запрещённый источник никогда не получает автоматический запрос.

### Этап 6 — эксплуатация и развитие

- [ ] Структурированные логи с автоматической редакцией секретов; локальные метрики OpenTelemetry без обязательной внешней SaaS-телеметрии.
- [ ] Accessibility WCAG 2.2 AA, keyboard/focus tests и `prefers-reduced-motion`.
- [ ] PWA только после manifest, service worker, offline/error UX и тестов обновления кеша.
- [ ] PostgreSQL, отдельная очередь, Grafana/Loki и нагрузочные тесты — только после измеренного роста; не усложнять одиночную установку заранее.
- [ ] Adapter contract tests для каждого нового источника и документированный restore drill перед релизом.

### Стратегия слияния без варианта «оставить оба»

Автоматически гарантировать правильный выбор при любом смысловом конфликте Git не может. Глобальный merge-driver `ours/theirs` опасен: он способен молча удалить исправления. Поэтому применяется контролируемая стратегия, при которой канонической всегда становится новая реализация:

1. Один PR меняет один feature и владеет отдельным каталогом; общие файлы (`App.tsx`, lockfile, OpenAPI) меняются в выделенном интеграционном коммите.
2. Перед merge новая ветка **rebase-ится на актуальную целевую ветку**. Конфликт разрешается внутри новой ветки переносом нужного актуального поведения в новую структуру; merge не предлагает владельцу проекта выбирать старый или оба варианта.
3. Если файл заменяется, используется двухшаговая схема: сначала добавляется новый модуль и переключатель, затем отдельным PR удаляется старый. Одновременное редактирование старого и нового файла запрещено.
4. После переключения старый экспорт удаляется целиком; не допускаются суффиксы `Old`, `New`, `V2`, дубли компонентов и закомментированный legacy-код.
5. Миграции и API остаются обратно совместимыми минимум один релиз. Generated OpenAPI client и lockfile всегда пересоздаются из канонического источника, а не объединяются вручную.
6. При конфликте приоритет имеет не «последний текст», а новая архитектура **плюс все прошедшие regression-тесты старого поведения**. Решение фиксируется тестом, чтобы конфликт не повторился.

### Definition of Done для каждого изменения

- [ ] Изменение маленькое, атомарное, имеет migration/rollback note и не смешивает рефакторинг с новой функцией.
- [ ] Unit, integration, E2E, accessibility и visual checks соответствующего слоя прошли; production build не содержит console errors.
- [ ] Нет нового обязательного платного сервиса, карты или облачного API; documented offline/local fallback проверен.
- [ ] Секреты отсутствуют в bundle, URL, логах, fixtures, screenshots, export и постоянном browser storage.
- [ ] README/OpenAPI/schema обновлены; старый код после переключения удалён, дубликатов нет.
- [ ] Измерены bundle/performance изменения, а feature flag и процедура отката проверены.

### Критическая оценка и корректировки плана

| Риск первоначального подхода | Почему это недостаток | Принятое решение |
| --- | --- | --- |
| Сразу разделить монолит и добавить backend | Большой diff скрывает регрессии и создаёт тяжёлые конфликты | Сначала baseline, затем по одному feature за совместимым adapter |
| PostgreSQL + Redis/BullMQ уже в MVP | Лишние процессы усложняют бесплатный локальный запуск | FastAPI + SQLite и in-process queue; масштабирование только по метрикам |
| Полагаться на «бесплатные» Gemini/Groq/OpenRouter | Квоты и условия могут измениться | Шаблонный режим обязателен, Ollama локален, облако опционально |
| Обещать несколько job-источников | У API разные лицензии, схемы и лимиты | Один read-only adapter после правовой проверки, затем contract-based расширение |
| Ранняя автоматическая отправка | Риск дублей, блокировки и нарушения правил | Сначала поиск/черновик/review; отправка только через официальный API и idempotency |
| Принудительный Git merge `theirs` | Молча теряет свежие исправления целевой ветки | Rebase, изолированное владение файлами, двухшаговая замена и regression gates |
| «Добавить тесты» без приоритета | Можно получить много тестов без защиты критического пути | Сначала пять smoke-сценариев, безопасность и дедупликация, затем расширение пирамиды |
| PWA и observability раньше core-функций | Увеличивают поверхность ошибок без продуктовой ценности | Перенесены после реального источника, безопасных черновиков и надёжной очереди |

## Критерии готовности production

- Никакие токены не попадают в URL, frontend bundle, логи, экспорт или постоянное browser storage.
- Повторный запуск не создаёт повторный отклик; каждый внешний side effect имеет idempotency key.
- Частичная недоступность источника не ломает весь поиск и явно видна пользователю.
- Письмо основано только на фактах профиля, доступно для просмотра и редактирования до отправки.
- Есть unit, integration и E2E проверки критического пути, CI блокирует merge при ошибках.
- Пользователь может скачать и удалить свои данные, остановить задачи и отозвать доступ.

## Правовые и этические ограничения

Перед автоматизацией необходимо проверить пользовательские соглашения и правила API каждого источника. Продукт не должен обходить CAPTCHA, скрытые лимиты или блокировки. Предпочтительный режим — поиск и подготовка черновиков; массовая отправка без осознанного подтверждения повышает риск блокировки аккаунта и ухудшает качество найма.
